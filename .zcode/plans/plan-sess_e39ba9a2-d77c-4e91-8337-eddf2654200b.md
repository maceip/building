# Execution plan: finish the three pillars honestly

**Priority:** make the native reliability SDK the third pillar. Keep the existing Quality Lab as its interface; stop adding generic dashboards instead of the missing capabilities.

## Verification rule

Every checkbox below starts **unchecked**. An independent observer verifies the actual APK/behavior—not the implementing agent’s explanation. It reports only **PASS, FAIL, or BLOCKED**, with one existing test result or direct observation.

**No new reporting framework, tracking files, monitoring service, or verification-only product code.** Use normal tests, APK inspection, ADB, screenshots and Play Console. Keep this checklist in the conversation. A mock or emulator result cannot satisfy a gate requiring a real account or physical device.

## 1. Resolve the embedded Play Console boundary first

- Test a minimal, manually operated embedded Console against the real Google flow before promising integration.
- Use supported native/browser Google authorization. Do not assume an API token signs the WebView into Console; do not copy cookies, inject credentials, spoof the browser, or automate legal declarations.
- If Google blocks the embedded authenticated experience, retain a Custom Tab/browser handoff and explicitly mark **embedded Console blocked**. Do not count the fallback as delivery of embedding. No promises to bypass setup, testing, eligibility or review.

**External gate**
- [ ] Observer sees a genuine authenticated, manually usable embedded Console through supported behavior—or records BLOCKED. No simulated screen or browser fallback is accepted as an embedded-view pass.

## 2. Build the durable, local-first reliability SDK

- Extend the existing small Java/Kotlin app-log runtime rather than embedding Node/Python for telemetry.
- Add bounded persistent crash/event storage, lifecycle breadcrumbs, previous-process exit information where supported, and explicit networking-client hooks. Exclude request bodies, credentials and personal payloads by default.
- Integrate with both native builds and real Gradle builds. Identify the exact app build/source revision.
- Replace the current weak Binder handshake with explicit IDE targeting, caller identity validation, pairing/revocation, bounded messages and acknowledged delivery. Preserve normal Android crash handling.
- Collection is explicit per project. Production telemetry and debug-only fault controls are separate; release apps contain no remotely callable test-control interface.

**External gate**
- [ ] On the physical Pixel, an instrumented fixture crashes while the IDE is closed/offline. Reopening delivers the retained incident once, associated with the correct build; a spoofing app is rejected and planted secrets are absent. Repeat with native-built and Gradle-built fixtures.

## 3. Add optional developer-owned relay delivery

- Use the same event format and durable queue for an explicitly configured HTTPS endpoint. Keep local-only operation fully functional.
- Authenticate, encrypt, retry with limits, deduplicate, cap storage and provide deletion/disconnect controls. Remote collection and sending evidence to a cloud AI provider require separate consent.

**External gate**
- [ ] Observer sees zero outbound telemetry when disabled; events from a second device arrive at the developer’s endpoint after an outage, without duplicate incidents. Invalid credentials/certificates fail closed.

## 4. Connect crashes to automatic AI repair

- Add incident-reading tools to the existing agent. Match the incident to its source revision before changing anything.
- A per-project opt-in can authorize automatic diagnosis, isolated patching, rebuilding and test execution—without copying a bug report into chat or approving every harmless step again.
- Preserve the full diff and original workspace, bound repair attempts, and support cancellation/rollback. Installation follows Android’s authorization rules. No automatic production deployment.

**External gate**
- [ ] Observer introduces a known bug, triggers it, and watches the opted-in agent receive the incident, patch and rebuild. The **same untouched reproducer fails before and passes afterward**, with a separate functional assertion still passing. Disabled/cancelled automation does not modify the original workspace.

## 5. Implement native Android failure testing

- Use ordinary Android instrumentation plus debug-only SDK hooks—not web-process tests presented as Android coverage.
- Cover activity recreation/background return, process kill/relaunch, interrupted work, controlled network failures, and signed app upgrades/database migrations.
- Exercise the app’s actual networking/storage code. Inject timeout, 401/429/500, malformed/partial responses and recovery through supported client adapters.
- Supply fixtures and assertions for saved drafts/selections, retained records, bounded retries and correct user-visible errors. Clearly distinguish injected failures from actual device/network conditions.

**External gate**
- [ ] Observer runs the unchanged native fixture suite on the physical Pixel: recreation, kill/relaunch, network failure/recovery and v1-to-v2 migration. Each seeded broken implementation fails its assertion; the corrected implementation passes without deleting data or weakening tests.

## 6. Add cooperating-app cross-device backup and restore

- Back up **participating apps’ selected user data**, not merely IDE projects and not arbitrary apps’ private storage.
- Define explicit export/import hooks, consistent snapshots, versioned schemas, integrity checks, encryption and a user-controlled recovery mechanism.
- Support direct archive transfer and the optional developer relay. Restore into staging, validate/migrate, then commit atomically; preserve existing data on failure. Credentials/signing keys are excluded by default.

**External gate**
- [ ] Observer transfers a populated fixture from Device A to a fresh installation on Device B and verifies records, attachments and settings. An older-schema restore works; corruption, a wrong key and interrupted restore leave existing destination data intact.

## 7. Embed Node and Python into generated apps

- Add separate optional Android engine libraries and a small Java/Kotlin host API. Run each engine in an app-owned private process/service; do not copy the IDE’s Termux prefix into generated production apps.
- Package native engines through APK/AAB delivery and application scripts/assets at build time. Integrate lifecycle, bounded I/O, cancellation and the reliability SDK.
- First prove actual engine embedding; only advertise tested modules/package capabilities. Keep the static-web wrapper distinct from server/runtime embedding. Process separation is not a security sandbox.

**External gate**
- [ ] Observer installs separate generated Node and Python apps on the Pixel, removes/stops the IDE, disables networking, and runs their real application logic. Both survive supported restart/update flows, stop cleanly, and report failures. No dependency on an IDE-hosted server is allowed.

## 8. Remove mandatory runtime weight and close distribution obligations

- Separate engine payloads from the IDE’s core. For Play distribution, use signed on-demand feature delivery; for direct distribution, offer core and engine-inclusive packages. Do not replace bundling with an unrestricted off-Play native downloader.
- Generated apps include only their selected engine. Remove unnecessary CLI/build-only components.
- Complete source, patch, build-configuration and license-notice obligations for the exact binaries—not another “audit later” disclaimer. Validate release signing, AAB structure and native alignment.

**External gate**
- [ ] Same-configuration core debug APK is **≤200 MiB**, contains no Node/Python payload, and still edits/builds native Android projects. Selecting an engine installs the signed component and it works offline afterward. Observer checks corresponding-source/notices against the shipped binaries. Production runtime claims also require a real 16-KiB-device check, not alignment inspection alone.

## 9. Replace weak grouping with evidence-backed semantic triage

- Reuse the existing AI-provider interface for multilingual structured classification; keep a clearly labeled offline heuristic option. No private archive upload without consent.
- Preserve citations, issue/PR distinctions and explicit repository exclusions. Group symptoms without asserting unverified causes.
- Freeze an independently reviewed, repository/language-stratified holdout. Keep related duplicates out of opposite splits; do not tune on its labels.

**External gate**
- [ ] Observer evaluates the frozen holdout: **≥80% primary-label agreement at ≥80% coverage**, with source-backed excerpts. Report language/repository breakdowns and specialized-case misses. Missing either threshold is FAIL—not hidden by increased abstention.

## 10. Prove live publishing and physical-device delivery

- Use a user-owned test app and approved credentials. Publish one fresh, genuinely signed version to the **internal test track**, using the supported API flow and any necessary manual Console steps.
- Require explicit approval of the account, package, artifact and destination before live writes. Do not change production.

**External gate**
- [ ] Observer sees the new version in the real Console, installs/updates it through Google Play on the physical Pixel, and verifies package/version and launch. Production remains unchanged. An accepted API request alone does not pass.

## Completion and communication

- Work in this order: feasibility/access checks; SDK/local delivery; relay and AI loop; native tests and backups; app embedding and optional delivery; grouping; live acceptance. Embedding feasibility can run alongside SDK work.
- Send only short milestone updates or genuine blockers. No repeated subagent-completion messages.
- Final handoff lists implemented, independently verified and blocked items separately. No “all three complete” claim while a required gate is unchecked.

**External gate**
- [ ] Observer matches every completion claim to its passed gate and the exact final artifact. No fresh reporting machinery was added to the project.

**Required for the external gates:** an authorized physical Pixel, a second Android device for transfer, access to a real 16-KiB device, developer-owned relay credentials, and a user-owned Play test app/OAuth/signing setup. Missing access means BLOCKED; it is never replaced with fabricated success or an unlabeled simulator result.
